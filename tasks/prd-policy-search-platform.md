# PRD: 청년·소상공인 통합 정책 검색 플랫폼

## 문서 정보

- 문서 상태: 초안
- 작성일: 2026-08-04
- 프로젝트 디렉터리: `policy-search-backend`
- MVP 배포 대상: 사용자의 AWS Lightsail 인스턴스
- 초기 데이터 범위: `cameleonh/youth-search`와 `djfksjd/sole-search`가 사용하는 출처

## 1. 개요

청년 사장님은 개인 자격으로 받을 수 있는 청년정책과 사업체 자격으로 받을 수 있는 소상공인 지원을 서로 다른 서비스에서 반복해서 찾아야 한다. 정책 공고는 HTML뿐 아니라 HWP, HWPX, PDF, DOCX, XLSX 같은 첨부파일에 핵심 자격조건을 담는 경우가 많고, 공고 표현도 기관마다 달라 단순 키워드 검색만으로는 실제 지원 가능성을 판단하기 어렵다.

본 제품은 청년정책과 소상공인 지원사업을 매주 미리 수집하여 PostgreSQL에 적재하고, 사용자가 한 번 입력한 개인·사업체 정보로 두 종류의 지원을 동시에 검색한다. 명확한 자격조건은 결정론적 규칙으로 판정하고, 정보가 부족하거나 공고가 모호한 정책은 `가능성 있음`으로 제공한다. 원문 검색과 설명에는 PostgreSQL 전문검색 및 벡터 검색을 결합한 RAG를 사용한다.

원본 첨부파일은 비공개 GitHub 아카이브 저장소의 주간 Release에 보관한다. Kordoc이 원본을 Markdown과 구조화 블록으로 변환하고, 후속 처리기가 검색 청크 및 자격조건을 생성한다. 최초 버전은 사용자 계정 없이 동작하며 입력 프로필을 DB나 애플리케이션 로그에 저장하지 않는다.

## 2. 문제 정의

현재 사용자는 다음 문제를 겪는다.

1. 개인 지원과 사업체 지원을 별도로 검색해야 한다.
2. 정책 제목이나 요약만으로는 실제 자격조건을 알기 어렵다.
3. 원문 첨부파일의 표와 예외조건을 직접 읽어야 한다.
4. 정보가 조금 부족하다는 이유로 받을 수 있는 정책이 검색에서 누락될 수 있다.
5. 공고가 수정되거나 삭제되면 당시 판정 근거를 재현하기 어렵다.

## 3. 대상 사용자

### 3.1 MVP 대상

- 대한민국에서 사업을 운영하거나 창업을 준비하는 청년
- 개인 자격 지원과 사업체 자격 지원을 한 번에 확인하려는 사용자
- 정책명을 모르더라도 자신의 상황을 기준으로 후보를 찾으려는 사용자

### 3.2 향후 대상

- 프로필을 저장하고 새 정책 알림을 받으려는 가입 사용자
- 수집 실패와 판정 품질을 관리하는 운영자
- 정책 데이터를 API로 활용하려는 외부 서비스

## 4. 목표

- 하나의 요청으로 개인 지원과 사업체 지원을 함께 검색한다.
- 매주 두 기존 저장소의 출처를 수집하고 신규 또는 변경 정책만 버전으로 추가한다.
- 모든 검색 결과에 판정 이유와 추적 가능한 원문 근거를 제공한다.
- 명확한 탈락 조건이 없는 불완전한 후보를 `가능성 있음`으로 보존한다.
- 동일한 원본 파일을 중복 업로드하거나 중복 파싱하지 않는다.
- 원본, 변환 결과, 구조화 조건 사이의 출처 관계를 재현 가능하게 유지한다.
- MVP에서는 사용자 프로필을 영구 저장하지 않는다.

## 5. 비목표

MVP에는 다음을 포함하지 않는다.

- 회원가입, 로그인, 저장된 프로필
- 개인화 알림, 이메일, 문자, 카카오톡 발송
- 지원사업 자동 신청 또는 신청서 자동 제출
- 사용자의 최종 법적·행정적 자격 보증
- `youth-search`와 `sole-search` 이외의 신규 출처 확장
- RDF/OWL 기반의 완전한 온톨로지 또는 별도 그래프 데이터베이스
- 모바일 네이티브 애플리케이션
- 원본 바이너리를 PostgreSQL에 저장하는 기능
- 기존 두 저장소의 코드를 하나의 저장소로 병합하거나 폐기하는 작업

## 6. 핵심 제품 원칙

### 6.1 판정과 검색의 분리

- 나이, 지역, 업력, 매출, 업종, 신청기간 및 명시적 제외조건은 구조화 규칙으로 판정한다.
- 전문검색과 벡터 검색은 관련도 순위와 원문 근거 탐색에 사용한다.
- RAG 또는 LLM은 결정론적 탈락 조건을 뒤집을 수 없다.
- 구조화 규칙과 생성된 설명이 충돌하면 구조화 규칙을 우선하고 충돌을 기록한다.

### 6.2 결과 상태

- `eligible` / 지원 가능: 필요한 입력이 갖춰졌고 모든 알려진 필수조건을 충족한다.
- `possible` / 가능성 있음: 명확한 탈락 조건은 없지만 입력이 부족하거나 공고 표현이 모호하다.
- `ineligible` / 지원 어려움: 하나 이상의 명시적 필수조건을 충족하지 않는다. 기본 결과 목록에서는 제외하되 내부 판정 근거는 유지한다.

### 6.3 근거 우선

- 모든 자격조건은 원본 문서, 섹션, 문단, 표 또는 셀 위치로 역추적할 수 있어야 한다.
- 근거가 없는 추론은 확정 조건으로 저장하지 않는다.
- 변환 실패 또는 부분 파싱 문서는 `지원 가능`으로 확정하지 않는다.

## 7. 사용자 경험

### 7.1 초기 입력 방식

MVP는 웹 폼으로 시작한다. 한 화면에서 개인 정보와 사업체 정보를 함께 받되, 사용자가 모르는 항목은 비워 둘 수 있어야 한다.

개인 정보 예시:

- 생년월일 또는 나이
- 거주 지역
- 취업 또는 구직 상태
- 소득 구간
- 관심 지원 유형

사업체 정보 예시:

- 예비창업 또는 사업자 여부
- 개업일 또는 업력
- 사업장 소재지
- 업종
- 연 매출 구간
- 상시근로자 수

### 7.2 결과 화면

결과는 `지원 가능`과 `가능성 있음`을 구분해 제공하고, 개인 지원과 사업체 지원을 같은 응답에서 확인할 수 있어야 한다. 각 정책 카드는 다음 정보를 포함한다.

- 정책명과 시행기관
- 개인 지원, 사업체 지원 또는 양쪽에 해당하는 범주
- 판정 상태
- 판정 이유
- 추가로 확인하거나 입력해야 할 정보
- 지원 내용
- 신청 기간과 마감 상태
- 공식 공고 링크
- 판정에 사용한 원문 근거

## 8. 사용자 스토리

### US-001: 통합 프로필 입력

**설명:** 청년 사장님으로서 개인 정보와 사업체 정보를 한 번만 입력하여 두 종류의 지원을 함께 찾고 싶다.

**수용 기준:**

- [ ] 개인 및 사업체 입력 필드가 한 화면에 제공된다.
- [ ] 사용자가 모르는 선택 필드는 비워 둘 수 있다.
- [ ] 제출 전에 필드 형식과 필수 최소 입력을 검증한다.
- [ ] 입력값은 검색 요청 처리 후 DB에 저장되지 않는다.
- [ ] 민감한 입력값은 평문 애플리케이션 로그에 남지 않는다.
- [ ] 타입 검사와 린트가 통과한다.
- [ ] dev-browser 스킬을 사용하여 브라우저에서 검증한다.

### US-002: 개인·사업체 지원 통합 결과

**설명:** 사용자로서 한 번의 검색으로 개인 지원과 사업체 지원 후보를 동시에 보고 싶다.

**수용 기준:**

- [ ] 하나의 API 응답에 개인 지원과 사업체 지원이 모두 포함될 수 있다.
- [ ] 결과는 `지원 가능`과 `가능성 있음`으로 구분된다.
- [ ] 명확한 탈락 정책은 기본 결과에서 제외된다.
- [ ] 동일 정책이 양쪽 범주에 해당하면 중복 카드가 아니라 하나의 결과로 표시된다.
- [ ] 타입 검사와 린트가 통과한다.
- [ ] dev-browser 스킬을 사용하여 브라우저에서 검증한다.

### US-003: 판정 근거 확인

**설명:** 사용자로서 왜 해당 정책이 추천되었는지 원문에 근거해 확인하고 싶다.

**수용 기준:**

- [ ] 각 결과에 충족한 조건과 확인이 필요한 조건이 표시된다.
- [ ] 각 판정 근거가 문서와 블록 위치를 참조한다.
- [ ] 근거 원문과 공식 공고 URL을 열 수 있다.
- [ ] 부분 파싱 경고가 있는 문서는 사용자에게 확인 필요 상태로 표시된다.
- [ ] dev-browser 스킬을 사용하여 브라우저에서 검증한다.

### US-004: 주간 정책 수집

**설명:** 운영자로서 두 기존 저장소의 출처에서 정책을 매주 자동 수집하고 싶다.

**수용 기준:**

- [ ] 예약 작업이 일주일에 한 번 실행된다.
- [ ] 운영자가 같은 작업을 수동으로 다시 실행할 수 있다.
- [ ] 수집 실행별 시작·종료 시각, 출처별 성공 수, 실패 수를 기록한다.
- [ ] 재실행해도 동일 정책 버전과 첨부파일이 중복 생성되지 않는다.
- [ ] 한 출처의 실패가 다른 출처의 성공 데이터를 롤백하지 않는다.
- [ ] 수집기 단위 테스트와 계약 테스트가 통과한다.

### US-005: 원본 첨부파일 보관

**설명:** 운영자로서 삭제되거나 변경될 수 있는 정책 원본을 재현 가능한 형태로 보관하고 싶다.

**수용 기준:**

- [ ] 원본은 비공개 `policy-search-archive` GitHub 저장소의 주간 Release에 업로드된다.
- [ ] Release는 연도와 ISO 주차를 포함하는 예측 가능한 이름을 사용한다.
- [ ] 출처별 원본 묶음과 `manifest.json`을 Release 자산으로 제공한다.
- [ ] 매니페스트에 출처 URL, 수집 시각, 파일명, MIME 유형, 바이트 크기 및 SHA-256이 포함된다.
- [ ] 업로드 후 다운로드한 파일의 SHA-256을 다시 검증할 수 있다.
- [ ] 동일 SHA-256 파일은 다시 업로드하지 않고 기존 자산을 참조한다.

### US-006: Kordoc 문서 변환

**설명:** 시스템으로서 HWP/HWPX/PDF/Office 첨부파일을 검색 및 조건 추출이 가능한 구조로 변환하고 싶다.

**수용 기준:**

- [ ] 고정된 Kordoc 버전을 라이브러리 API로 호출한다.
- [ ] 지원 형식은 Markdown과 구조화 블록으로 변환된다.
- [ ] 문단, 표 및 셀의 원문 위치 정보가 보존된다.
- [ ] 파일 SHA-256, 파서 버전 및 옵션 해시가 같으면 재파싱하지 않는다.
- [ ] 암호화, 미지원 형식, 시간 초과 및 부분 파싱을 구분된 상태와 오류 코드로 기록한다.
- [ ] 변환 워커의 메모리, CPU, 파일 크기 및 실행 시간에 상한을 둔다.
- [ ] 정상 문서, 손상 문서, 암호화 문서 및 과대 문서 테스트가 통과한다.

### US-007: 자격조건 구조화

**설명:** 시스템으로서 공고의 자연어 조건을 재현 가능한 자격 규칙으로 변환하고 싶다.

**수용 기준:**

- [ ] 나이, 지역, 업력, 매출, 업종, 고용 상태, 신청기간 및 제외조건을 표현할 수 있다.
- [ ] AND, OR, NOT, 범위, 포함 목록, 제외 목록 및 미상 값을 표현할 수 있다.
- [ ] 명확한 조건은 규칙 기반 추출을 우선한다.
- [ ] 애매한 문장에만 LLM 기반 후보 추출을 사용할 수 있다.
- [ ] LLM 추출 결과에는 신뢰도와 원문 근거가 반드시 포함된다.
- [ ] 근거가 없거나 신뢰도 기준 미만인 조건은 확정 규칙으로 승격하지 않는다.
- [ ] 대표 정책 고정 데이터셋에 대한 회귀 테스트가 통과한다.

### US-008: 하이브리드 검색과 매칭

**설명:** 사용자로서 자격조건을 지키면서도 의미상 관련된 정책을 빠짐없이 찾고 싶다.

**수용 기준:**

- [ ] 구조화된 필수조건 판정을 검색 순위 계산보다 먼저 수행한다.
- [ ] PostgreSQL 전문검색과 벡터 검색 결과를 결합한다.
- [ ] 정보 부족은 탈락이 아니라 `가능성 있음`으로 처리한다.
- [ ] RAG 답변은 검색된 근거 청크만 인용한다.
- [ ] RAG 설명이 구조화 판정과 충돌하면 구조화 판정을 유지하고 충돌을 기록한다.
- [ ] 동일 입력과 동일 데이터 버전의 구조화 판정 결과는 결정론적이다.
- [ ] 매칭 및 검색 회귀 테스트가 통과한다.

### US-009: 수집·변환 상태 확인

**설명:** 운영자로서 최근 주간 작업이 정상 종료되었는지 확인하고 실패 항목만 재처리하고 싶다.

**수용 기준:**

- [ ] 실행별 상태가 `pending`, `running`, `partial`, `succeeded`, `failed`로 구분된다.
- [ ] 출처, 다운로드, 아카이브, 파싱 및 정규화 단계별 처리량과 오류를 확인할 수 있다.
- [ ] 실패 항목만 안전하게 재시도할 수 있다.
- [ ] 처리 중인 실행이 중복 예약되지 않는다.
- [ ] 사용자 입력이나 비밀값은 상태 화면 및 로그에 노출되지 않는다.

### US-010: Lightsail 단일 서버 배포

**설명:** 운영자로서 현재 AWS Lightsail 인스턴스에서 전체 MVP를 반복 가능하게 배포하고 싶다.

**수용 기준:**

- [ ] Docker Compose로 웹, API, 워커 및 PostgreSQL을 기동할 수 있다.
- [ ] PostgreSQL은 외부 포트를 공개하지 않고 내부 네트워크에서만 접근한다.
- [ ] PostgreSQL 데이터는 컨테이너 수명과 분리된 영속 볼륨에 저장한다.
- [ ] 수집 및 문서 변환 작업의 동시 실행 수를 제한하여 사용자 검색을 고갈시키지 않는다.
- [ ] 서비스 재시작 후 헬스체크와 기본 검색 스모크 테스트가 통과한다.
- [ ] 배포 문서에 초기화, 마이그레이션, 백업 및 복구 절차가 포함된다.

## 9. 기능 요구사항

### 9.1 수집

- FR-ING-001: 시스템은 `youth-search`와 `sole-search`가 사용하는 초기 출처 집합을 출처 ID로 관리해야 한다.
- FR-ING-002: 시스템은 각 출처를 독립적으로 수집하고 출처별 체크포인트를 기록해야 한다.
- FR-ING-003: 시스템은 매주 한 번 예약 수집을 실행해야 한다.
- FR-ING-004: 시스템은 운영자가 동일 파이프라인을 수동 실행할 수 있게 해야 한다.
- FR-ING-005: 시스템은 원격 공고 ID와 정규화된 URL을 기준으로 정책 후보를 식별해야 한다.
- FR-ING-006: 시스템은 공고 본문 또는 첨부파일 변경 시 기존 행을 수정하지 않고 새 정책 버전을 추가해야 한다.
- FR-ING-007: 시스템은 출처별 수집 성공과 실패를 분리 커밋해야 한다.
- FR-ING-008: 시스템은 허용된 출처와 다운로드 규칙만 사용해야 하며 임의 사용자 URL을 가져오면 안 된다.

### 9.2 GitHub 원본 아카이브

- FR-ARC-001: 원본 바이너리는 비공개 GitHub 아카이브 저장소에 저장해야 한다.
- FR-ARC-002: 주간 Release 태그는 `ingest-YYYY-Www` 형식을 사용해야 한다.
- FR-ARC-003: 자산 수 제한과 저장소 비대화를 피하기 위해 출처별 원본을 압축 묶음으로 업로드해야 한다.
- FR-ARC-004: 매니페스트는 각 원본의 압축 내부 경로와 SHA-256을 포함해야 한다.
- FR-ARC-005: 애플리케이션 API와 웹 컨테이너는 아카이브 쓰기 자격증명을 보유하면 안 된다.
- FR-ARC-006: 아카이브 업로더만 해당 비공개 저장소에 한정된 최소 쓰기 권한을 가져야 한다.
- FR-ARC-007: DB에는 원본 바이너리가 아니라 아카이브 좌표와 무결성 정보만 저장해야 한다.

### 9.3 변환 및 청크

- FR-DOC-001: 시스템은 파일 내용으로 형식을 감지하고 확장자만 신뢰하지 않아야 한다.
- FR-DOC-002: 시스템은 Kordoc의 고정 버전과 고정 옵션을 사용해야 한다.
- FR-DOC-003: 시스템은 변환 결과에 파서명, 파서 버전, 옵션 해시, 경고 및 오류 코드를 기록해야 한다.
- FR-DOC-004: 시스템은 제목, 문단, 목록, 표 및 셀 경계를 가능한 한 보존해야 한다.
- FR-DOC-005: 검색 청크는 문서, 페이지 또는 섹션, 블록 및 표 위치를 참조해야 한다.
- FR-DOC-006: 부분 파싱 문서는 검색할 수 있지만 확정 자격 판정에는 사용할 수 없어야 한다.
- FR-DOC-007: OCR은 필요한 파일에만 적용하고 실패 시 텍스트가 없는 상태를 명시해야 한다.

### 9.4 경량 온톨로지와 자격 규칙

- FR-ONT-001: 시스템은 정책, 정책 버전, 기관, 지역, 대상 유형, 혜택, 신청기간, 첨부파일 및 자격 규칙을 구조화해야 한다.
- FR-ONT-002: 자격 규칙은 버전이 있는 규칙 트리로 저장해야 한다.
- FR-ONT-003: 각 규칙 노드는 필드, 연산자, 값, 단위, 근거 위치, 추출 방식 및 신뢰도를 가져야 한다.
- FR-ONT-004: 시스템은 개인 조건과 사업체 조건을 분리하되 한 정책에 양쪽 조건을 함께 연결할 수 있어야 한다.
- FR-ONT-005: 정책 버전이 변경되면 해당 버전에 연결된 규칙도 불변 이력으로 남겨야 한다.

### 9.5 검색 및 RAG

- FR-SRCH-001: 검색 API는 개인 및 사업체 프로필을 하나의 요청으로 받아야 한다.
- FR-SRCH-002: 입력 프로필은 요청 수명 안에서만 사용하고 영속화하지 않아야 한다.
- FR-SRCH-003: 시스템은 먼저 결정론적 자격 규칙을 평가해야 한다.
- FR-SRCH-004: 알 수 없는 필드는 실패가 아니라 미상으로 평가해야 한다.
- FR-SRCH-005: 명확한 실패 규칙이 하나라도 있으면 내부 상태를 `ineligible`로 정해야 한다.
- FR-SRCH-006: 구조화 필터 후 전문검색과 벡터 검색을 결합해 순위를 계산해야 한다.
- FR-SRCH-007: 응답에는 상태, 이유, 부족한 정보, 혜택, 신청기간, 공식 URL 및 근거가 포함되어야 한다.
- FR-SRCH-008: 생성형 설명은 검색된 근거 밖의 자격조건을 새로 만들면 안 된다.
- FR-SRCH-009: 근거가 충분하지 않으면 추측하지 않고 확인 필요를 반환해야 한다.

### 9.6 운영

- FR-OPS-001: 모든 수집 실행과 단계는 상태, 카운터, 시작·종료 시각 및 오류 요약을 기록해야 한다.
- FR-OPS-002: 로그는 구조화 형식이어야 하며 실행 ID와 출처 ID로 검색 가능해야 한다.
- FR-OPS-003: 실패 재시도는 멱등적이어야 한다.
- FR-OPS-004: 실행 잠금으로 동일 예약 작업의 중복 실행을 방지해야 한다.
- FR-OPS-005: 서비스는 웹, API, DB 및 워커 헬스체크를 제공해야 한다.

## 11. 처리 흐름

```text
주간 스케줄 또는 수동 실행
  -> 두 출처 집합 수집
  -> 공고와 첨부파일 정규화
  -> SHA-256 계산 및 중복 확인
  -> 비공개 GitHub Release + 매니페스트 보관
  -> Kordoc 변환
  -> 문서 청크 생성
  -> 규칙 우선 자격조건 추출
  -> 애매한 조건만 LLM 후보 추출
  -> 검증된 정책 버전과 규칙을 PostgreSQL에 추가
  -> 전문검색 및 벡터 인덱스 갱신
  -> 실행 결과 기록
```

```text
웹 폼 제출
  -> 입력 검증 및 임시 프로필 정규화
  -> 구조화 자격 규칙 평가
  -> 명확한 탈락 후보 제외
  -> 전문검색 + 벡터 검색 결합
  -> 지원 가능 / 가능성 있음 분류
  -> 근거 기반 설명 생성
  -> 응답 후 임시 프로필 폐기
```

## 12. 기술 구성

### 12.1 저장소 형태

새로운 독립 모노레포를 사용한다.

```text
policy-search-backend/
  apps/
    web/                 Next.js 웹 UI
    api/                 FastAPI 검색 및 운영 API
  workers/
    ingest/              주간 출처 수집
    document-extract/    Node.js + Kordoc 문서 변환
    normalize/           정책·자격조건 정규화
  packages/
    matching/            결정론적 규칙 평가기
    contracts/           서비스 간 데이터 계약
  db/
    migrations/          PostgreSQL 마이그레이션
    views/               최신 버전 및 검색 뷰
  tasks/
    prd-policy-search-platform.md
```

### 12.2 런타임

- 웹: Next.js
- API: FastAPI
- 데이터베이스: PostgreSQL + 전문검색 + `pgvector`
- 문서 변환: Node.js 워커에서 Kordoc 라이브러리 API 호출
- 배포: 단일 AWS Lightsail 인스턴스의 Docker Compose
- 예약 실행: Lightsail 내부 스케줄러 또는 전용 스케줄 컨테이너

### 12.3 데이터베이스 운영

- PostgreSQL은 앱과 같은 Lightsail 인스턴스에서 실행한다.
- DB 포트는 인터넷에 공개하지 않는다.
- 데이터 볼륨은 컨테이너 이미지와 분리한다.
- 마이그레이션은 배포 전 단일 작업으로 실행한다.
- 주간 수집과 Kordoc 워커는 검색 API의 자원을 고갈시키지 않도록 동시성 및 자원 제한을 적용한다.
- 계정 기반 프로필을 도입하기 전에 별도의 암호화된 외부 백업과 복구 훈련을 필수화한다.

## 13. 오류 처리

| 상황 | 처리 방식 |
|---|---|
| 한 출처 수집 실패 | 해당 출처만 실패 처리하고 다른 출처 결과 유지 |
| 첨부파일 다운로드 실패 | 제한된 재시도 후 실패 상태 및 원본 URL 기록 |
| SHA-256 불일치 | 파싱·적재 금지, 무결성 오류로 격리 |
| GitHub Release 업로드 실패 | DB에 아카이브 완료로 표시하지 않고 재시도 가능 상태 유지 |
| Kordoc 부분 파싱 | 청크 검색 허용, 확정 자격 판정 금지 |
| 암호화 또는 DRM 문서 | 수동 확인 필요 상태로 보존 |
| LLM 응답 실패 | 규칙 기반 결과만 저장하고 문서를 재처리 대기열에 유지 |
| 벡터 생성 실패 | 전문검색은 제공하되 벡터 상태를 불완전으로 표시 |
| PostgreSQL 장애 | 요청 실패를 명시하고 수집 체크포인트를 전진시키지 않음 |
| RAG 근거 부족 | 설명을 생성하지 않고 확인 필요와 공식 링크 반환 |

## 14. 보안 및 개인정보

- 사용자 프로필은 MVP에서 DB, 분석 도구 및 로그에 저장하지 않는다.
- 요청 로그에는 필드 값 대신 요청 ID, 처리시간 및 결과 개수만 기록한다.
- 원격 문서 다운로드는 설정된 출처와 검증된 URL 규칙으로 제한한다.
- 파일 형식은 매직 바이트로 검증하고 크기, 압축 해제 크기, 페이지 수 및 처리시간을 제한한다.
- Kordoc 워커는 최소 권한, 임시 작업 디렉터리 및 제한된 네트워크로 실행한다.
- GitHub 자격증명은 아카이브 저장소에만 범위가 제한되어야 한다.
- 아카이브 쓰기 자격증명은 웹/API 컨테이너와 분리한다.
- 비밀값은 이미지, 저장소, 로그 또는 오류 응답에 포함하지 않는다.
- PostgreSQL은 Docker 내부 네트워크에서만 접근한다.
- 관리 작업은 인증된 운영 경로에서만 허용한다.

## 15. 성능 및 신뢰성 기준

- NFR-001: 구조화 규칙 판정은 동일 입력과 데이터 버전에 대해 동일한 결과를 반환해야 한다.
- NFR-002: 일반 검색 요청의 구조화 판정 및 검색 단계 p95는 Lightsail 운영 환경에서 2초 이하여야 한다. 생성형 설명 시간은 별도로 측정한다.
- NFR-003: 검색 결과의 100%는 공식 공고 URL을 포함해야 한다.
- NFR-004: `지원 가능` 또는 `가능성 있음` 결과의 100%는 최소 하나의 원문 근거를 포함해야 한다.
- NFR-005: 동일 파일 SHA-256의 중복 Kordoc 실행률은 0%여야 한다.
- NFR-006: 한 출처 실패 시 정상 출처의 신규 데이터는 계속 게시되어야 한다.
- NFR-007: 배포와 워커 재시작 후 중복 정책 버전이 생성되지 않아야 한다.

- Python API와 Node.js Kordoc 워커의 작업 메시지 계약
- GitHub Release 매니페스트 스키마

### 16.3 통합 테스트

- 수집부터 정책 버전 생성까지의 전체 파이프라인
- 원본 업로드, 재다운로드 및 SHA-256 검증
- Kordoc 변환부터 청크·규칙 적재까지의 흐름
- PostgreSQL 전문검색 및 벡터 검색 결합
- 실패 후 재시도와 멱등성

### 16.4 고정 평가 데이터셋

- 개인 조건만 있는 정책
- 사업체 조건만 있는 정책
- 개인과 사업체 조건을 함께 요구하는 정책
- 표 안에 핵심 조건이 있는 HWP/HWPX/PDF
- 명시적 제외조건과 예외조건이 있는 정책
- 입력 부족으로 `가능성 있음`이 되어야 하는 정책
- 부분 파싱 및 암호화 문서

### 16.5 브라우저 및 운영 검증

- 한 번의 폼 제출로 양쪽 정책 유형이 표시되는지 확인한다.
- 근거 링크, 빈 상태, 오류 상태 및 모바일 폭을 확인한다.
- 실제 Docker Compose 환경에서 헬스체크, 검색 및 주간 작업 스모크 테스트를 수행한다.
- 배포 후 대표 프로필로 검색 결과와 근거를 수동 확인한다.

## 17. 성공 지표

- 주간 예약 수집 성공률 95% 이상. 출처별 부분 실패는 별도 집계한다.
- 정상 다운로드한 지원 형식 문서의 Kordoc 처리 성공 또는 명시적 부분 성공률 95% 이상.
- 사용자에게 노출된 모든 결과의 공식 URL 및 원문 근거 포함률 100%.
- 고정 평가 데이터셋에서 명확한 탈락 조건을 `지원 가능`으로 잘못 분류하는 비율 0%.
- 고정 평가 데이터셋에서 기대한 `지원 가능` 또는 `가능성 있음` 상태 일치율 90% 이상.
- 동일 주간 작업 재실행 시 정책 버전과 원본 파일 중복 생성 0건.
- 대표 프로필 검색에서 개인 지원과 사업체 지원을 단일 응답으로 반환.

## 18. 단계별 범위

### Phase A: MVP

- 사용자 계정 없는 웹 폼
- 요청 단위 임시 프로필
- 두 기존 저장소의 출처
- 주간 append-only 수집
- 비공개 GitHub Release 원본 아카이브
- Kordoc 변환
- 경량 온톨로지와 결정론적 규칙 판정
- 전문검색 + 벡터 검색 + 근거 기반 RAG
- 지원 가능 및 가능성 있음 결과
- 단일 Lightsail + PostgreSQL 배포

### Phase B: 계정 기반 개인화

- 인증과 사용자 계정
- 암호화된 저장 프로필
- 관심 정책, 검색 기록 및 알림 설정
- 새 정책과 프로필의 재매칭
- 알림 채널
- 개인정보 보존·삭제 정책
- 외부 암호화 DB 백업과 복구 훈련

Phase B는 Phase A의 검색 계약과 정책 스키마를 재사용하며, `profile_id`와 인증 계층을 추가하는 방식으로 설계한다.

## 19. 출시 기준

MVP는 다음 조건을 모두 만족할 때 출시 가능하다.

- [ ] 두 초기 출처의 주간 수집과 수동 재실행이 성공한다.
- [ ] 원본 파일과 매니페스트가 비공개 GitHub Release에 저장되고 해시 검증된다.
- [ ] 대표 HWP/HWPX/PDF/Office 문서가 Kordoc으로 변환된다.
- [ ] 정책 버전, 청크 및 자격 규칙이 PostgreSQL에 적재된다.
- [ ] 동일 작업 재실행이 중복 데이터를 만들지 않는다.
- [ ] 한 번의 검색으로 개인 및 사업체 지원 결과가 반환된다.
- [ ] 지원 가능과 가능성 있음이 판정 이유 및 원문 근거와 함께 표시된다.
- [ ] 부분 파싱, 출처 실패 및 정보 부족 상태가 사용자와 운영자에게 구분된다.
- [ ] 단위, 계약, 통합 및 브라우저 핵심 시나리오가 통과한다.
- [ ] Lightsail에서 배포·재시작·마이그레이션·복구 절차가 검증된다.
- [ ] 비밀값과 사용자 입력이 저장소 및 로그에 남지 않는다.
